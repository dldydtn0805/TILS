# FSD
- FSD(Feature-Sliced Design)는 프론트엔드 애플리케이션을 스캐폴딩(안전하게 작업) 하기위한 아키텍처 방법론이다.
- 주요 목적은 변화하는 비즈니스 요구 사항에 직면하여 프로젝트를 보다 이해하기 쉽게 구조화하는 것이다.
- 폴더 구조는 최대 3단계이다.

![fsd.png](img/fsd.png)
## Layers

### Role

- 코드를 재사용의 범위와 의존성 규칙에 따라 수직적으로 나누어놓은 계층구조
- 코드를 구분하는 가장 큰 범위, 각 부분이 어떤 기능을 담당하는지, 다른 코드에 얼마나 의존하는지를 기준으로 한다.
- 필요한 레이어만 추가하여 사용할 수 있다.
- 위에서 아래로 단방향 의존성을 가진다. 예를들어 `~/features/benefit/ui/A.tsx`는 `~/shared/ui/B.tsx`를 import할 수 있지만, 반대는 불가능하다.

### Point
- 상위 레이어는 하위 레이어를 참조할 수 있는 단방향 의존성을 가진다 (app > pages > widgets > features > entities > shared)

| 구분       | 설명                                                                         | 특이사항                                              |
| -------- | -------------------------------------------------------------------------- | ------------------------------------------------- |
| App      | 앱 전체 에 영향을 주는 코드 ( 라우터 설정, 진입점 설정, 전역 상태관리, 전역 스타일, 프로바이더 )                | slice 없이 segment 로만 구성됨                           |
| Processes | 페이지 간 복잡한 시나리오                                                             | 더 이상 사용되지 않음                                      |
| Pages    | 전체 페이지 또는 중첩 라우팅에서 페이지의 주요 부분                                              | 대부분 페이지 1개는 슬라이스 1개 (단, 유사한 페이지는 하나의 슬라이스로 묶기 가능) |
| Widgets  | 독립적으로 작동하고 여러 페이지에서 재사용되는 대규모 기능 또는 UI 컴포넌트 . 보통 하나의 완전한 기능                |                                                   |
| Features | 제품 전반에 걸쳐 재사용되는 기능 구현체로, 사용자에게 실질적인 비즈니스 가치를 제공하는 동작 ( 동사적 개념 )            |                                                   |
| Entities | 프로젝트가 다루는 비즈니스 데이터 ( 명사적 개념 )                                              |                                                   |
| Shared   | 앱의 기본 구성 요소 를 모아둠. 재사용 가능한 기능, 특히 프로젝트/비즈니스의 특성과 분리되어 있을 때 (반드시 그럴 필요는 없음) | slice 없이 segment 로만 구성됨<br><br>                   |


## Slices

### Role
- 레이어 내에서 코드를 비즈니스 도메인별로 분할
- 슬라이스의 이름은 표준화되어있지 않고, 비즈니스 도메인에 따라 결정된다.
- 같은 레이어 안에서 다른 슬라이스를 참조할 수 없다. 이러한 특징이 높은 응집도와 낮은 결합도를 유지하는데 도움이 된다.
- 도메인의 코드들이 슬라이스별로 모여있도록 자연스럽게 구성된다 -> 높은 응집도
- 같은 레이어 내에서 다른 슬라이스를 참조할 수 없다 -> 낮은 결합도

### Point
- 같은 레이어 안에서는 다른 슬라이스를 참조할 수 없다. (높은 응집도, 낮은 결합도 유지에 도움)

## Segments

### Role
- 슬라이스 내에서 코드를 기술적 목적에 따라 구분

### Point
- 이름은 ui, api, model 등 목적을 설명해야한다 (components, hooks 같은 성격은 지양)

| 네이밍    | 설명                      | 예시                                                       |
| ------ | ----------------------- | -------------------------------------------------------- |
| ui     | UI와 관련된 모든 것            | UI 컴포넌트, 날짜 포맷터, 스타일 등                                   |
| api    | 백엔드 통신 및 데이터 로직         | request 함수, 데이터 타입, mapper 등                             |
| model  | 애플리케이션 도메인 모델           | 스키마, 인터페이스, 스토어, 비즈니스 로직 (Redux/Zustand의 액션, 리듀서, 셀렉터 등) |
| lib    | 슬라이스 내에서만 사용하는 라이브러리 코드 |                                                          |
| config | 설정 파일과 feature-flag 파일  |                                                          |

## 전체 구조

```
└─ src
    ├─ app : 앱 전체에 영향을 주는 코드(라우터 설정, 진입점 설정, 전역 상태 관리, 전역 스타일, 프로바이더)
    │	├─ routes
    │	├─ store
    │	├─ styles
    │	├─ entrypoint
    │	└─ ...
    ├─ pages : 전체 페이지 또는 중첩 라우팅에서 페이지의 주요 부분
    │	├─ benefitList
    │	│	├─ ui
    │	│	├─ api
    │	│	└─ ...
    │	├─ benefitDetail
    │	│	└─ ...
    │	└─ ...
    ├─ widgets : 독립적으로 작동하고 여러 페이지에서 재사용되는 대규모 기능 또는 UI 컴포넌트. 보통 하나의 완전한 기능
    │	├─ benefitItem
    │	│	├─ ui
    │	│	└─ ...
    │	└─ ...
    ├─ features : 제품 전반에 걸쳐 재사용되는 기능 구현체, 사용자에게 실질적인 비즈니스 가치를 제공하는 동작 (동사적 개념)
    │	├─ benefit
    │	│	├─ config
    │	│	├─ model
    │	│	├─ api
    │	│	├─ ui
    │	│	└─ ...
    │	├─ coupon
    │	│	├─ config
    │	│	├─ model
    │	│	├─ api
    │	│	├─ ui
    │	│	└─ ...
    │	└─ ...
    ├─ entities : 프로젝트가 다루는 비즈니스 데이터 (명사적 개념)
    │	├─ benefit
    │	│	├─ model
    │	│	├─ api
    │	│	├─ ui
    │	│	└─ ...
    │	├─ coupon
    │	│	├─ model
    │	│	├─ api
    │	│	├─ ui
    │	│	└─...
    │	└─ ...
    └─ shared : 앱의 기본 구성 요소를 모아둠, 재사용가능한 기능, 특히 비즈니스 프로젝트/비즈니스의 특성과 분리되어있을 때(반드시 그럴 필요는 없음)
    ├─ api
    ├─ ui
    ├─ lib
    ├─ config
    ├─ routes
    ├─ i18n
    └─ ...
```

## Advantage
- 구조가 명확하여, 팀간 협업 및 신규 작업자 온보딩이 용이하다.
- 추가 기능 작업 시 사이드 이펙트 발생 확률이 줄어든다. (레이어와 슬라이스로 코드가 구분된다.)
- 유지 보수성이 향상된다.
- 재사용 가능한 코드 레벨과 지역적으로만 사용하는 코드 레벨을 레이어에 따라 구분할 수 있다.
- 아키텍처 구성 요소를 쉽게 교체, 추가, 제거 가능하다.
- 아케텍처 표준화가 가능하다.
- 확장성이 높다.
- 비즈니스 지향적이다.
- 모듈간 연결이 제어되고 명시적이다.

## Disadvantage

- 다른 아키텍처 솔루션에 비해 높은 진입 장벽이 있다.
